# Backend Project Documentation 🚀

This document outlines the architecture, setup, and key functionalities of the backend FastAPI application, including database management and schema generation utilities. It's designed for flexibility, allowing you to define different database schemas for various projects through a simple YAML configuration and supports both local and cloud database instances with real-time data streaming.

## 🚀 Overview: How the Code Works

This backend API leverages **FastAPI** for the web interface, **asyncpg** for asynchronous database interactions with **TimescaleDB**, and **Pydantic** for dynamic data validation.

Here's a breakdown of the key components and their roles in the current project structure:

1. **`config/schema.yml`**: This YAML file is the heart of the dynamic schema. It defines the names of your database tables, their columns, and the corresponding PostgreSQL data types. It also specifies which column should be used as the hypertable time dimension for TimescaleDB. It now includes the dedicated `frontend_configs` table schema for UI settings.

2. **`utilities/generate_models.py`**: This script acts as a code generator. When run manually (or potentially at Docker build time), it reads `config/schema.yml` and **statically generates Pydantic `BaseModel` classes** for each table defined in the schema. These generated models are written to `api/autogenerated/generated_models.py`. This step is crucial for enabling IDE autocomplete and static type checking during development, as well as providing strong validation for API payloads.

3. **`api/autogenerated/generated_models.py`**: This file contains the actual Pydantic models generated by `utilities/generate_models.py`. It's a derived file and **should not be edited manually**.

4. **`api/schema_models.py`**: This module is responsible for loading the *raw* schema definition from `config/schema.yml` into a Pydantic `SchemaConfig` model (`LOADED_RAW_SCHEMA`). This raw schema data is used by the API and utility scripts for various operations, such as constructing `CREATE TABLE` SQL statements and understanding table structures.

5. **`api/models.py`**: This file contains common Pydantic models used across the API, most notably the `ApiResponse` model for standardized responses. Crucially, it now also defines the `FrontendConfigData` Pydantic model for validating UI configuration payloads. It imports all dynamically generated Pydantic models from `api/autogenerated/generated_models.py` using `from api.autogenerated.generated_models import *`, making them accessible throughout the API package.

6. **`api/data_router.py`**: This module defines an `APIRouter` with the prefix `/database`. It contains all the core data-related interaction endpoints, including creating tables, inserting/retrieving data, synchronizing to cloud, and the unified WebSocket for live data.

   * It uses `backend_api.state.local_db_pool` (an `asyncpg` connection pool) to acquire and release database connections asynchronously.

   * Incoming data for inserts is validated against the statically generated Pydantic models.

   * All SQL queries are executed using `asyncpg`'s non-blocking methods.

   * It's also responsible for **broadcasting newly inserted data to active WebSocket clients**.

7. **`api/ui_router.py`**: This new module defines an `APIRouter` with the prefix `/ui`. It is specifically designed to handle endpoints for managing frontend application configurations, providing a clean separation from data operations.

8. **`api/__main__.py`**: This is the main entry point for the FastAPI application.

   * It initializes the FastAPI `backend_api` instance.

   * It sets up Loguru for consistent logging.

   * Crucially, it handles the **`asyncpg` connection pool lifecycle** (local and cloud), creating pools on application startup and closing them on shutdown.

   * It initializes the **WebSocket broadcasting queues** and **active client lists** for real-time data streaming.

   * It includes both the `data_router` and `ui_router` to mount all database and UI-related endpoints.

   * It defines a basic health check endpoint (`/`).

9. **`docker-compose.yml`**: This file orchestrates all services (TimescaleDB, API, Grafana). It manages environment variables, port mappings, and service dependencies, loading configuration from the `.env` file.

## ⚙️ Core Configuration Files

### `config/database_configs.yml`

This YAML file centralizes all database connection configurations, allowing you to easily manage multiple local and cloud database instances across different deployment environments (`development`, `production`).

**Key Features:**

* **Environment-Specific Settings**: Defines distinct connection details for each environment.

* **Flexible Cloud Instances**: Uses a list of `cloud_dbs` with `name` and `url`, removing the need for hardcoded counts or indexed environment variables.

* **Cloud Sync Toggle**: Each environment has an `enable_cloud_db` flag to easily enable or disable cloud synchronization.

**Example Structure:**

```yaml
development:
  enable_cloud_db: false # Set to true to enable cloud sync
  local_db_url: postgresql://user:password@localhost:5432/metrics_db_dev
  cloud_dbs:
    - name: dev_cloud_primary
      url: postgresql://dev_user:dev_password@dev-cloud-host-1:5432/dev_db_1
    # ... more cloud instances
production:
  enable_cloud_db: true
  local_db_url: postgresql://prod_user:prod_password@timescaledb:5432/metrics_db_prod
  cloud_dbs:
    - name: prod_cloud_main
      url: postgresql://prod_user:prod_password@prod-cloud-host-main:5432/prod_db_main
    # ... more cloud instances

```

### `config/schema.yml`

This YAML file defines the database schemas (tables, columns, data types, hypertable columns) for your application. It serves as the single source of truth for your database structure.

**Key Features:**

* **Dynamic Schema Definition**: Tables and their columns are defined declaratively.

* **Hypertable Support**: Specifies which column to use for TimescaleDB hypertable creation.

* **`frontend_configs` Table**: Includes a dedicated table for storing UI configurations, ensuring `client_id` is unique and `config_data` uses `JSONB`. Note that `frontend_configs` is *not* created as a hypertable due to its primary key constraint.

**Example Structure:**

```yaml
tables:
  sensor_data:
    columns:
      time: TIMESTAMPTZ NOT NULL
      device_id: TEXT NOT NULL
      temperature: DOUBLE PRECISION
      humidity: DOUBLE PRECISION
    hypertable_column: time
  frontend_configs: # For UI configurations
    columns:
      client_id: TEXT NOT NULL UNIQUE
      config_data: JSONB
      last_updated: TIMESTAMPTZ NOT NULL
    hypertable_column: last_updated # Not used for hypertable creation for this table

```

## 🛠️ Utility Scripts (`backend/utilities/`)

The `utilities` folder contains essential scripts for managing database setup and Pydantic model generation.

### `generate_models.py`

This script reads `config/schema.yml` and automatically generates Pydantic models in `api/autogenerated/generated_models.py`. These models are crucial for FastAPI's request validation and response serialization, and they enable excellent IDE autocomplete and static type checking during development.

**Usage:**
Run this script whenever `config/schema.yml` is updated to ensure your Pydantic models are in sync with your database schema.

```bash
# Navigate to the 'backend' directory first
cd backend/
python -m utilities.generate_models

```

### `db_manager.py`

This powerful script facilitates comprehensive database management for both local and configured cloud instances. It ensures databases exist, creates tables, and supports resetting environments.

**Available Actions:**

* **`setup`**: Creates tables (including `frontend_configs`) based on `schema.yml` and ensures they are set up as hypertables where specified. Can target local, all cloud, or a specific cloud database.

* **`reset`**: Drops all tables and then recreates them. Can target local, all cloud, or a specific cloud database.

* **`auto_setup`**: The recommended action. It automatically ensures the target databases exist and then sets up all tables in the current environment's local DB and all enabled cloud DBs.

**Key Options with `auto_setup`:**

* **`--drop-local-existing`**: When used with `auto_setup`, it drops all existing tables in the **local database** before recreating them. Ideal for a fresh local environment.

* **`--drop-cloud-existing`**: When used with `auto_setup`, it drops all existing tables in the **cloud database(s)** before recreating them. Use with caution for cloud environments!

**Examples:**

```bash
# Navigate to the 'backend' directory first
cd backend/

# Run a full automatic setup for the 'development' environment
# (Creates tables if they don't exist, skips cloud DBs if enable_cloud_db: false)
python -m utilities.db_manager --action auto_setup

# Run a full automatic setup, dropping existing tables in the local DB first
python -m utilities.db_manager --action auto_setup --drop-local-existing

# Run a full automatic setup, dropping existing tables in enabled cloud DBs first
# (Cloud DB sync must be enabled in config/database_configs.yml for the environment)
python -m utilities.db_manager --action auto_setup --drop-cloud-existing

# Run a full automatic setup, dropping existing tables in BOTH local AND cloud DBs first
python -m utilities.db_manager --action auto_setup --drop-local-existing --drop-cloud-existing

# Reset (drop and recreate) a specific table in the local database
python -m utilities.db_manager --action reset --target local --table sensor_data

# Create tables in all configured cloud databases (if enabled)
python -m utilities.db_manager --action setup --target cloud_all

```

## 🚀 FastAPI Application (`backend/api/`)

The FastAPI application serves as the core backend, providing data and UI configuration services.

### `__main__.py` (Main Application Entry)

* Initializes database connection pools (local and multiple cloud instances) using configurations from `config/database_configs.yml`.

* Loads the database schema from `config/schema.yml` using `api/schema_models.py`.

* Sets up **WebSocket broadcasting queues** and **active client lists** for real-time data streaming, dynamically creating consumers for each defined table.

* Registers both the `data_router` and `ui_router` to expose their respective API endpoints.

* Defines a basic health check endpoint (`/`) to confirm the API is running and report key status information.

### `data_router.py` (Data Endpoints)

This router (`/database` prefix) handles all operations related to sensor data and other time-series data.

* **`POST /database/create_table/{table_name}`**: Creates a table and sets it as a TimescaleDB hypertable based on `schema.yml`. Also attempts to create the table on all configured cloud databases if enabled.

* **`POST /database/insert_data/{table_name}`**: Inserts a batch of records into the specified table. Each record is validated against the statically generated Pydantic model. After successful local insertion, it **broadcasts new data to active WebSocket clients** subscribed to that table and pushes data to all configured cloud databases if enabled.

* **`GET /database/get_data/{table_name}`**: Retrieves historical data from the specified table. Reads only from the local database, supporting `limit` and `order_by_column` parameters.

* **`POST /database/synchronize_all_tables`**: Forces a one-way synchronization of all local data to configured cloud databases. This is useful for populating cloud instances with existing local data.

* **`WEBSOCKET /database/ws/data/{table_name}`**: A unified WebSocket endpoint that provides a seamless data stream. Upon connection, it first sends a batch of historical data (configurable with the `historical_limit` query parameter) and then seamlessly transitions to streaming live data as new records are inserted into the database. This approach effectively eliminates the "gap" problem on frontend plots after a page reload.

### `ui_router.py` (UI Configuration Endpoints)

This new router (`/ui` prefix) is dedicated to managing frontend application settings.

* **`models.py` Integration**: It uses the `FrontendConfigData` Pydantic model (defined in `api/models.py`) for validating incoming configuration payloads, ensuring data integrity.

* **`GET /ui/config/{client_id}`**: Retrieves the saved UI configuration for a specific frontend client. This allows custom dashboard/plot settings to persist across browser reloads or sessions.

* **`POST /ui/config/{client_id}`**: Saves or updates the UI configuration for a client. It utilizes an "upsert" mechanism (insert if not exists, update if exists) based on the `client_id` in the `frontend_configs` table, ensuring efficient storage of user preferences.

## ⚙️ Modifying Schemas and Configurations for Different Deployments

The project is designed to keep deployment-specific configurations separate from the core code, using `.env` for environment variables and `config/` files for database schemas and connections.

### Environment Variables (`.env`)

For deployment-specific settings, use the `.env` file located in the project root. This file is loaded by Docker Compose and automatically makes the variables available to your services.

**File**: `./.env`

```bash
# ./.env
# This file defines environment variables used by Docker Compose and the API.

# API Service Configuration
API_PORT=5000

# TimescaleDB Configuration
POSTGRES_DB=metrics_db
POSTGRES_USER=user
POSTGRES_PASSWORD=password

# Grafana Configuration
GRAFANA_ADMIN_USER=admin
GRAFANA_ADMIN_PASSWORD=admin_password

```

**To modify**: Simply edit the values in `.env`. After changes, run `docker-compose down && docker-compose up --build` to ensure all services pick up the new environment variables.

### Database Schemas (`config/schema.yml`)

To define or alter your database tables and their column structures, you'll modify `config/schema.yml`.

**File**: `./config/schema.yml`

```yaml
# ./config/schema.yml
tables:
  sensor_data:
    columns:
      time: TIMESTAMPTZ NOT NULL
      device_id: TEXT NOT NULL
      temperature: DOUBLE PRECISION
      humidity: DOUBLE PRECISION
    hypertable_column: time
  frontend_configs: # For UI configurations
    columns:
      client_id: TEXT NOT NULL UNIQUE
      config_data: JSONB
      last_updated: TIMESTAMPTZ NOT NULL
    hypertable_column: last_updated # Not used for hypertable creation for this table
  # Add more tables as needed...

```

**To modify**:

1. Edit `config/schema.yml` to add, remove, or modify table/column definitions.

2. **Crucially**, after any changes to `config/schema.yml`, you must **regenerate the Pydantic models** and rebuild your Docker image, then use `db_manager.py` to apply schema changes to your database:

   ```bash
   # Navigate to the 'backend' directory
   cd backend/
   
   # 1. Regenerate Pydantic models
   python -m utilities.generate_models
   
   # 2. Rebuild Docker services (important for the API to pick up new generated models)
   docker-compose down
   docker-compose up --build
   
   # 3. Update database tables (e.g., for local development)
   #    Use --drop-local-existing cautiously if you have existing data!
   python -m utilities.db_manager --action auto_setup --drop-local-existing
   
   ```

   This ensures that your API's validation logic matches the new schema and the database tables are correctly created or updated.

## 👨‍💻 Developing with This Code

### Initial Setup

1. **Clone the Repository**:

   ```bash
   git clone your-repo-url backend
   cd backend
   
   ```

2. **Create `.env`**: Copy the example `.env` content from above into a file named `.env` in the project root (`backend/`). Adjust values as needed.

3. **Generate Pydantic Models**:

   ```bash
   python -m utilities.generate_models
   
   ```

   This will create `api/autogenerated/generated_models.py`.

4. **Build and Run Services**:

   ```bash
   docker-compose up --build
   
   ```

   This command will build the Docker images (including running `generate_models.py` inside the container for the API service), start TimescaleDB, the FastAPI API, and Grafana.

5. **Setup Database Tables**: After services are running, apply your schema to the database(s).

   ```bash
   python -m utilities.db_manager --action auto_setup --drop-local-existing # Use --drop-local-existing for a fresh start
   
   ```

### IDE and Autocomplete

Because `utilities/generate_models.py` creates `api/autogenerated/generated_models.py` as a concrete Python file, your IDE (VS Code, PyCharm, etc.) will be able to perform **static analysis** and provide **autocomplete** for the Pydantic models.

For example, in `api/data_router.py`, when working with `PydanticModel(**data)` or iterating through results, you'll get autocomplete for fields like `validated_data.time`, `validated_data.device_id`, etc.

### Live Reload for API Development

For local development, you might want to enable live reloading for the API. You can modify the `command` in `docker-compose.yml` for the `api` service:

```yaml
    command: ["uvicorn", "api.__main__:backend_api", "--host", "0.0.0.0", "--port", "${API_PORT:-5000}", "--reload"]

```

Remember to remove `--reload` for production deployments, as it can have performance implications.
